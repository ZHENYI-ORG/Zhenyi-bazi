# 真一「盲派做功判盘引擎」技术设计白皮书 v1.0

> 文档性质：研发冻结前设计稿 / Codex 可执行开发蓝图  
> 核心目标：把“八字排盘软件”升级为“不依赖大模型也能完成结构判盘”的确定性判盘系统。  
> 研究基线：匿名化内部研究语料（核心资料、系统资料与研究笔记）、现有生产增强技法库、确定性事实层修复计划与当前生产提示词。  
> 重要说明：本文件忠实区分“资料明确支持的命理规则”与“为了软件工程稳定性作出的设计决定”。书中案例与术数理论属于传统命理材料，并不构成现代科学验证；本系统的工程目标是**稳定、可复算、可审计地实现所选理论体系**，而不是把术数包装成科学概率模型。

---

# 0. 结论先行

经过对内部研究资料的交叉研究，之前“事实图谱 → 宾主 → 体用 → 做功 → 归属 → 主线”的方向是正确的，但仍少了几个决定系统是否真正像“老师傅看盘”的关键层。

最终架构不能只是“规则匹配器”，而应至少包含：

1. **Fact Engine**：只负责可机械复算的事实。
2. **Relation Semantic Engine**：把“有冲/有合”进一步判成当前语境中的冲动、冲开、冲破、合留、合绊等，但必须经过规则门禁。
3. **Contextual Guest–Host Engine**：宾主是分层、相对的，不能把“年月=宾、日时=主”永久写死在节点上。
4. **Ten-God Intent Engine**：十神含义会因所生、所制、所合对象而改“意向”。
5. **Qi-Shi Engine**：识别党势/气势，作为主线和正反局的重要参照。
6. **Dynamic Ti-Yong Engine**：体用属于“路径角色”，不能把一个十神永久固定为体或用。
7. **Gong Path Engine**：枚举制用、合用、化用、生泄用、墓用及复合做功。
8. **Gong Validator**：区分有效成立、条件成立、仅有意向、反局/被破坏、不成立。
9. **Ownership Engine**：回答“最后归谁”，这是产品最有辨识度的一层。
10. **Zheng/Fan Arbiter**：判断日干、日支、主位与全局意向是否同向。
11. **Mainline Arbiter**：不是“命中规则最多者胜”，而是选择真正的第一做功主线。
12. **Xiang Engine**：做功不是唯一方法；无明显做功或需要细化时必须能进入象法路径。
13. **Timing Engine**：原局定题，大运定阶段，流年完成或触发。
14. **Evidence & Audit Engine**：任何判断都能回溯到“事实 → 关系 → 机制 → 归属 → 反证 → 应期”。

这套架构的核心产品语义是：

> **不只告诉用户八个字是什么，而是告诉他：这张盘想做什么、谁在做功、用什么方式做、最终成果落到谁手里，以及哪一步运会启动或破坏这条主线。**

# 1. 研究结论与资料依据

## 1.1 盲派入手顺序不是“旺衰优先”

核心资料反复给出的入手顺序是：

- 先看日干；
- 日干有合，先看它合什么、想取得什么；
- 日干无合，再看有无生，即食伤输出；
- 日干不做功，再看日支；
- 日支看刑、冲、克、穿、墓、合、成党成势；
- 日干日支都不明显，再看禄、比劫及其是否做功；
- 做功不是唯一方法，必要时转象法。

**工程结论：**
`DayMasterIntentResolver` 必须先于普通的 `GongCandidateDetector`。不能扫全盘所有生克后简单按分数选最大。

---

## 1.2 宾主不是一个静态字段

资料中至少存在这些宾主层次：

- 日主 vs 其他干支；
- 日柱 vs 其他柱；
- 日时 vs 年月；
- 原局 vs 大运流年；
- 原局+大运 vs 太岁；
- 在不同六亲、事业、财富问题中，同一字的“主/宾”解释还会发生上下文变化。

**工程结论：**
禁止：

```ts
node.guestHost = "guest";
```

应改为：

```ts
resolveGuestHost(nodeId, context): GuestHostState
```

也就是说，宾主是 `contextual relation`，不是节点永久属性。

---

## 1.3 体用必须动态

资料的基础倾向是：

- 日主、印、禄、比劫偏体；
- 财、官杀偏用；
- 食神、伤官可体可用。

但同一个食伤，在“食伤生财”“印制食伤”“食伤制杀”中角色完全不同。

**工程结论：**
体用只存在于 `GongPath` 内：

```ts
{
  nodeId: "...",
  role: "body" | "use" | "tool" | "target" | "bridge" | "result"
}
```

不能在基础命盘数据中永久标注“这个十神永远是体”。

---

## 1.4 十神必须有“意向层”

内部核心资料 C及函授资料明确展示：

- 食神本可表示才华；
- 当它去生财时，意向可转为“求财方法/手段”；
- 同样的伤官，因为旁边所连接的官杀、财、印不同，现实含义也会改变。

**工程结论：**
必须有：

```text
TenGodIntentResolver
```

它输出的不是“庚=食神”这种基础身份，而是：

```json
{
  "base_ten_god": "食神",
  "current_intents": [
    "output",
    "wealth_generation"
  ],
  "evidence_paths": ["..."]
}
```

十神基础身份由事实层计算；“当前意向”由关系与做功上下文决定。

---

## 1.5 气势/党势必须独立建模

资料把“势”作为高等级做功与正反局判断的重要基础。大富贵类命例经常不是靠单字，而是某一党/某一势共同完成对目标的制化。

**工程结论：**
新增：

```text
QiShiResolver
```

但气势绝不能用“同类字数量 >= 3”这种粗糙规则直接判断。至少考虑：

- 月令是否支持；
- 根气；
- 三合/三会；
- 连续生助；
- 是否存在明显对立党；
- 主位是否加入该势；
- 这个势是否真正参与做功。

输出例如：

```json
{
  "id": "qishi_fire_earth_01",
  "elements": ["fire", "earth"],
  "members": ["..."],
  "support": ["month_order", "root", "continuous_generate"],
  "direction": "control_water",
  "confidence": "high"
}
```

---

## 1.6 “有关系”绝不等于“有功”

资料与现有生产规则都强调：

- 合、冲、刑、穿、克、墓首先只是动作；
- 必须看对象、方向、能否取得、是否产生结果、结果归谁；
- “食伤和财都出现”不等于食伤生财已经做成；
- “财在盘里”不等于财属于命主。

**工程结论：**
必须把：

```text
RelationFact
```

与：

```text
GongEffect
```

彻底分离。

---

## 1.7 同一个“冲”有不同语义

资料中出现的冲语义包括：

- 冲动
- 冲开
- 冲去
- 冲破
- 冲旺
- 冲制
- 冲出

并且原局、大运、流年的语境不同；例如资料常把“流年冲墓”与“大运冲墓”分开处理。

**工程结论：**

第一层：

```json
{
  "type": "clash",
  "left": "...",
  "right": "...",
  "layer": "liunian"
}
```

第二层才允许生成：

```json
{
  "semantic": "store_open",
  "gate": "passed",
  "evidence": ["..."],
  "source_rule": "..."
}
```

绝不能：

```text
辰戌冲 → 自动开库
```

---

## 1.8 同一个“合”也有不同语义

资料区分：

- 合留
- 合绊
- 合动
- 合去
- 合伤
- 合变

并且日干合年月官与合时上官，在部分内部资料中就有不同意向解释。

**工程结论：**
`combine` 必须是事实，`combine_semantic` 必须由上下文规则决定。

---

## 1.9 墓库必须成为独立子系统

资料反复提醒最容易误判的是：

- 墓
- 库
- 入墓
- 坐库
- 藏于库支
- 冲库
- 刑库
- 合闭
- 开库
- 出库
- 开后归主还是外流

**工程结论：**
单独开发 `TombStoreEngine`，不得把墓库逻辑散落在各个规则中。

核心流程：

```text
固定库身份
→ 谁可能入库
→ 是否真的入墓
→ 当前库是谁控制
→ 当前动作是开 / 破 / 闭 / 收 / 释放
→ 出来后流向哪里
→ 结果归谁
```

---

## 1.10 做功五类是骨架，但还要支持复合结构

资料系统性列出：

- 制用
- 化用
- 生/泄用
- 合用
- 墓用
- 复合结构

**工程结论：**
`GongPathEnumerator` 不应该只有五个 detector；必须支持多跳图路径。

例如：

```text
食神
  ↓ 制
七杀
  ↓ 统财
财
  ↓ 承接
日时主位
```

这是一个复合路径，而不是三条独立规则简单相加。

---

## 1.11 做功效率不能直接做成“82分”

资料讨论“能量与效率”，也举例说明：

- 制用一般比单纯相生效率高；
- 强势去弱目标与相生取得现实层级不同；
- 有巨大气势但只制一个很弱的目标，功量仍小；
- 结果落在宾位，即使做功存在，也可能主要表现为替平台/单位做结果。

但书中还有把“几层功”直接对应财富金额、官职级别的具体说法。这类映射缺乏现代统计验证，不应成为软件直接输出。

**工程决定：**
内部采用**序位等级**，不采用“财富金额/官职级别”的硬映射：

```text
G0 = 无有效功
G1 = 有意向 / 弱作用
G2 = 有效单路径
G3 = 闭环主线
G4 = 多节点复合 / 气势参与
G5 = 多层复合且结果稳定归主
```

然后同一等级内部再比较力量、稳定性、归属与反证。

---

## 1.12 “功归谁”应成为真一核心能力

资料和现有生产规则都不断强调：

- 财在宾位不等于本人发财；
- 有平台资源不等于本人掌权；
- 有项目金额不等于利润归本人；
- 开库以后如果外流，也不能算资产归主；
- 做功者、成果承接者、最终所得者必须分开。

**工程结论：**
`OwnershipResolver` 是一级核心模块，不是报告解释层。

最终必须输出四种之一：

```text
mostly_native
shared
mostly_external
unclear
```

并必须给出证据链。

---

## 1.13 正局/反局必须独立裁决

资料将反局分为：

- 原局反局
- 大运反局
- 流年反局

核心不是“某字凶”，而是：

> 原局本来想做 A，但另一个关键作用反而保护 A、破坏功神，或日干/日支对同一目标表达相反意向。

**工程结论：**
必须有 `ZhengFanResolver`，并且它依赖：

- `IntentGraph`
- `QiShi`
- `GongPath`
- `RelationSemantic`

不能单独靠十神喜忌判断。

---

## 1.14 做功不是唯一入口，必须保留“象法”

内部核心资料 A明确给出：有些命局没有明显刑冲克穿墓合做功，却仍需通过象法理解；理法和象法也可能同时存在。

资料中常见象法包括：

- 共象
- 合象
- 化象
- 墓象
- 换象
- 带象
- 借象
- 局象
- 制象（当前生产体系中也在使用）

**工程结论：**
新增独立：

```text
XiangEngine
```

但它的权限必须低于“事实”和“已成立的结构”，作用主要是：

1. 在无明显主功时提供第二解释路径；
2. 对已成立主功做现实对象细化；
3. 绝不能凭单一象点直接钉死疾病、犯罪、职业、婚姻事件。

---

## 1.15 应期必须保持“三层”

现有生产规则和资料共同支持：

```text
原局：什么事
大运：哪个阶段
流年：何时完成/引动
```

**工程结论：**
禁止从流年反推原局不存在的事件。

`TimingEngine` 只接受已经建立的 `OriginalTheme` / `GongMainline`。

# 2. 资料冲突与“不能直接写死”的项目

这一章非常重要。开发前必须先冻结口径。

## 2.1 三合“成局”与“化”的口径

资料中存在不同表述：

- 有资料强调三合三支齐全即可成局，不以天干透出作为成局门槛；
- 对“参与合局的每个字是否完全失去原属性”又提出需要根据生克、原神等具体判断；
- 当前生产增强规则中则倾向把“成局”与“是否化/是否归主”继续分开检查。

**最终设计：**

```text
formation = 是否成局
transformation = 某节点是否发生功能改性
ownership = 成局结果归谁
```

三件事分开，禁止一个 boolean `isSanHe=true` 包办全部。

---

## 2.2 “旺衰”权限

部分核心研究资料强调不以日主旺衰作为论命核心；当前项目的混合理论提示词则已经把旺衰降级为：

- 工具力量
- 承载能力
- 稳定性
- 原局兑现度

**工程决定：**
`Strength/Capacity` 保留，但权限严格限制：

```text
它可以：
- 调整 GongPath 状态
- 调整稳定性
- 判断工具能否承载

它不可以：
- 重新定义第一主线
- 仅凭身强弱决定吉凶
- 覆盖宾主体用与已成立做功
```

---

## 2.3 特殊暗合/暗冲/相绝

不同资料版本之间口径不完全一致。

**工程决定：**
全部进入：

```text
SchoolSpecificRelationRegistry
```

规则必须具备：

- 来源
- 所属流派
- 精确组合
- 适用层
- 前置条件
- 反证条件
- 状态：verified / school_specific / case_only / disputed

未入白名单绝不计算。

---

## 2.4 功量对应具体财富金额/官阶

部分内部资料有明确量级映射。

**工程决定：**
只保留“功量相对大小”的方法，不把金额和官阶映射生产化。

原因：

1. 资料中的映射属于教学口诀/案例归纳；
2. 没有独立统计验证；
3. 对现代不同经济环境不可直接外推；
4. 软件应避免伪精确。

---

## 2.5 神煞权限

部分盲派高级资料真正重点使用的“神煞”很少，而当前排盘产品已经有 200+ 神煞。

**工程决定：**

- 200+ 神煞继续作为“排盘展示/查询”能力；
- `BlindJudgmentEngine` 不让普通神煞决定第一主线；
- 只有经过专门白名单验证的少数神煞/特殊象法允许作为 `supporting_evidence`；
- 神煞永远不得覆盖 A/S 级结构闭环。

# 4. 核心数据模型

## 4.1 FactNode

```ts
type Layer = "original" | "dayun" | "liunian";

interface FactNode {
```

# 6. 规则治理：比写规则更重要

## 6.1 双轴分级

### 轴 A：资料状态

```text
verified         已核实
school_specific  流派专用
case_only        案例归纳
disputed         争议隔离
```

### 轴 B：证据等级

```text
S  核心书籍明确方法 + 多处重复 + 逻辑完整
A  系统资料有方法说明 + 有实例
B  学生笔记/单次断语/条件不完整
C  网络转述/无法确认/与核心资料冲突
```

## 6.2 生产准入

| 状态 | S/A | B | C |
|---|---|---|---|
| verified | 可进入核心 | 只能辅助 | 禁止 |
| school_specific | 白名单进入 | 只能辅助 | 禁止 |
| case_only | 不自动直断 | 不自动直断 | 禁止 |
| disputed | 隔离 | 隔离 | 隔离 |

---

## 6.3 每条规则必须保存来源

```ts
interface RuleSourceRef {
  fileId?: string;
  fileName: string;
  chapter?: string;
  locator?: string;
  sourceType:
    | "core_book"
    | "system_course"
    | "lecture_notes"
    | "internal_engineering";
}
```

内部规则可以有工程权重，但必须明确：

```text
engineering_only = true
```

不能伪装成“师门原法”。

---

# 7. 主线裁决算法

禁止：

```text
命中规则最多 → 第一主线
```

建议词典序：

1. `effective > conditional > intent_only > broken`
2. 能否直接连接命主/主位与核心目标
3. 路径是否闭合
4. 结果是否明确
5. 结果归主程度
6. 是否有气势/党势支持
7. 日干/日支是否参与
8. 与全局意向是否一致
9. 功神是否有根/有来源
10. 反证数量与强度
11. 同柱/贴身优先于遥远关系
12. 大运是否正在支持该线

同级仍无法分时允许：

```text
co_primary = true
```

不能为了 UI 强行随机排出第一。

---

# 8. 做功等级：分类优先，评分其次

内部先分类：

```text
L0 无功 / 只有废神
L1 仅有做功意向
L2 条件成立
L3 有效单路径
L4 有效闭环 + 归属明确
L5 气势/复合路径/多节点共同完成
```

同层内部才用辅助 score 排序：

```ts
score = {
  pathCompleteness,
  ownershipClarity,
  hostParticipation,
  actorStability,
  targetControl,
  qishiSupport,
  counterEvidencePenalty
}
```

**禁止对用户展示“成功概率 87%”“财富 82 分”。**

# 9. Xiang Engine 权限

象法分两种场景。

## 场景 A：做功已成立

象法只负责：

```text
结构 → 更具体的现实对象
```

例如把“食伤输出 + 某五行/宫位”缩小到某种职业功能。

## 场景 B：无明显做功

允许象法成为 `primary_fallback`，但必须：

- 至少两个象点同向；
- 有宫位/干支/十神中的两层支持；
- 无强反证；
- 不输出重大健康、犯罪、死亡等结论。

# 10. 岁运引擎

## 10.1 大运

大运不只“加强/削弱五行”，而是判断它对原局主线：

```text
complete
amplify
weaken
reverse
replace_mainline
neutral
```

## 10.2 流年

流年必须绑定：

```text
originalMainlineId
```

如果原局没有这件事，流年不能自己创造。

## 10.3 应期三层

高置信应期至少满足：

```text
原局主题
+
大运阶段
+
流年完成动作
```

不足三层时降低确定性。

1. 不允许把自然语言口诀直接散落进业务代码。

4. 所有关系必须先存在 `RelationFact` 才能生成语义。
5. 未进入白名单的暗合/暗冲不得计算。
6. `Root`、`Origin`、`Ownership` 必须是三个不同概念。
7. `GuestHost` 必须支持上下文，不能永久写死在 node。
8. `TiYong` 必须属于 path。
9. 一个盘有多条路径时必须全部枚举后再裁决。
10. 不允许找到第一条规则就 `return`。
11. 没有明确第一主线时允许 `co_primary` 或 `unclear`。
12. 岁运不得凭空创造原局不存在的事件。
13. Xiang 不得越权覆盖明确结构事实。
14. 神煞不得覆盖核心做功主线。
15. AI 不得重新计算核心判断。

# 19. 当前最重要的后续研究任务

虽然本设计已经足够用于启动 Phase 0，但以下内容还不能直接宣称“全部冻结”：

1. 暗合/暗冲/相绝的最终白名单；
2. 三合“成局”与节点“改性”的统一口径；
3. 墓库“多而墓 / 一而墓 / 同党墓”的完整条件；
4. 合制、冲制、穿制在不同方向的效率口径；
5. 正向/反向做功在事业、财富以外主题中的上下文；
6. 换象的可迁移条件；
7. 功量只保留序位以后，如何做内部同层排序；
8. 部分学生笔记与核心书籍冲突时的优先级；
9. 十神意向规则怎样从自然语言转成机器 DSL；
10. 书中命例去重：不同书可能重复同一原始案例，不能把重复出版当成多次验证。

这些内容应在 `Phase 0 — 知识冻结` 完成，而不是让 Codex 在编码过程中临场决定。

# 20. 最终产品定义

这个引擎一旦做准，真一的差异化不应该再写：

> 200+神煞 / 真太阳时 / 专业细盘 / AI解析

而应该是：

> # 真一判盘
> **看清一张命盘到底在做什么。**

产品核心三问：

> **谁在做功？**  
> **最后归谁？**  
> **什么时候真正启动？**

排盘是底座，判盘才是产品。
